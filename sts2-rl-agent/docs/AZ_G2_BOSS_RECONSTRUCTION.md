# G2.3b1：Boss 原生重建、状态牌与容量

日期：2026-10-13。接续 G2.3a。**本步完成 G2.3b 的重建与状态牌依赖；完整训练接入仍未完成。** 没有新实验、模型、训练成绩或 Boss 胜率。前一批 G2.2b 的结果保持原样。

## 交付

- `boss_reconstruction.py`：不可变、可 JSON 序列化的 Boss 敌人快照；从公开事件推导阶段和多爪计数，再创建原生 AI 闭包并恢复当前状态。快照仅含阶段事件、HP、格挡、公开能力量，不含真实对象、实例 ID、RNG、私有 AI 日志或回调。
- 原生 `create_test_subject` 新增两个仅供重建的可选计数参数，默认均为零，正常遭遇创建规则保持不变。参数进行严格整数及阶段检查。初始工厂仍创建第一阶段基础对象，重建调用方必须在启动粒子战斗后恢复快照；不能把计数参数当作可直接开玩的后期遭遇配置。
- 恢复器验证自己创建的对象与计数匹配，拒绝错误闭包。恢复不重放过去攻击、复活或生成牌，不产生历史副作用；恢复后的复活行动仍须实际执行。Nemesis 的交替标记和 Intangible 的跳过衰减位从公开阶段历史推导，并仅写入新粒子。
- `boss_cards.py`：独立暂存 Burn／Wound 编解码器，继承上一批卡牌工厂，拒绝不存在的升级状态牌；旧 SUMMON 编解码器仍拒绝它们，没有隐式扩大旧版本内容。
- 可计算容量上界 2145，暂存动作宽度 4096，单选保留每个候选位置；Purity 集合仍只使用低九位。超过已证明容量时明确报错，不截断。

重建 API 使用顺序：`create_enemy(snapshot, rng)` → 加入新粒子并 `start_combat()` → `restore_enemy(enemy, ai, snapshot)`。它只重建敌人；玩家、牌堆、支付历史、选择回调及整个信息状态仍由未来 Boss 适配器恢复。不得把原局传入此 API，也不得把敌人对照测试称为完整搜索粒子验收。

## 验证

新增 59 项测试：重建 43 项、状态牌／容量 16 项。加上 G2.3a 的 46 项，共 105 项 Boss 定向检查。

- 25 个公开边界（第一／二／三阶段，不同行动计数，以及前两阶段击倒状态）分别创建两个独立粒子；原局和其中一个粒子连续执行八个后续敌方回合，逐步比较公开敌状态、玩家 HP／格挡／能力及新增状态牌。兄弟粒子保持原样，能力对象不共享。
- 专门验证第二阶段击倒后的复活为 300 HP 第三阶段，避免闭包计数归零而回到第二阶段。
- 串行与两个 spawn 工作进程分别重建五个阶段快照，未来五个回合结果完全一致。
- 扰动原局私有 AI 状态不影响快照；非法能力、错误版本、错误工厂闭包和永久死亡快照被拒绝。
- Burn 对 0／1／2／10 格挡造成 2／1／0／0 实际 HP 损失，Wound 无回合末伤害；保留后两者均不按 Dazed 的虚无规则消失。
- 真实 Headbutt 选择包含 2145 个候选，最后一个候选可完整编码、解码并回到堆顶。该测试是容量边界构造，不是声称该牌量在标准战斗中必然可达。
- 原生 Purity 可选择并消耗两种状态牌；Armaments+ 不制造 Burn+／Wound+。

这些战斗夹具使用高 HP、受控击倒及敌方回合操作，仅用于机制与重建验证，不是策略质量评估。冻结源码后的全量回归：6,637 passed、1 skipped、30 subtests passed，用时 161.54 秒。全量回归记录 `az_boss_reconstruction_tests.txt`，验收记录 `az_boss_reconstruction_acceptance.json`。
