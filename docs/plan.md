> 第 6 节的决定已由用户做出（见该节）。2026-11-18 工作区翻新后，文中的 `unified_obs` / `unified_net` 对应 `train/spire_rl/obs.py` / `net.py`，C++ 观察在 `sim/src/combat_obs.cpp`、`sim/src/macro_obs.cpp`，吞吐测试是 `train/scripts/bench_throughput.py`。旧训练线的经过见 `DEVLOG.md`。

## 0. 结论

把训练方式改成 AlphaDefect 那样：**一个网络打整局（局外选择加每一手出牌），不搜索，纯 PPO，大批量、多并行**，再加上它的三个技巧：**练习战（难的多练）、价值函数可以看隐藏信息、EMA 权重加取最大评估**。

我们已有的东西大部分能用：C++ 模拟器、战斗与局外的实体观察（`unified_obs`）、统一网络的结构（`unified_net`，实体集合加候选打分，与 AlphaDefect 同一类）。要放弃的是：MCTS 打战斗、局外单独的 small 网络、8 步历史、分叉。

成败取决于**吞吐量**。现在约 18 万个决策/小时；本机实测模拟器加观察编码单核每个决策约 0.15 毫秒（随机打法），所以引擎不是瓶颈，瓶颈在 Python 的组织方式和 GPU 推理的批量。目标是每秒 1 万个决策以上（约 3,600 万/小时，是现在的 200 倍），这样 Zero-Search 论文那样的 16.6 亿个决策约两天。

## 1. AlphaDefect 的 README 说了什么

用户贴来的总览页（仓库 `hmty-CHEN/alphadefect-evaluation-runs`，本机连不上 GitHub，各次评估的 README 还没看）：

- 四个角色各一个模型：故障机器人、储君、静默、Fool。**没有铁甲战士。** 每个都从零开始只用强化学习训练，不用人类对局、不模仿、没有手写策略、不跨角色继承权重。
- 网络约 1,800 万到 2,000 万参数。输入是每个可见对象一条记录（手牌、抽牌堆、弃牌堆、消耗堆、牌组、敌人与意图、能力、遗物、药水、充能球、地图节点、界面选项），Transformer 一起读；引擎列出所有合法动作，网络按动作涉及的记录和整体状态给每个动作打分，softmax 得到概率。
- 价值估计只在训练时用，可以用打牌时看不到的信息（如抽牌堆真实顺序）；策略看不到这些信息。
- PPO，大量并行的无界面引擎（跑游戏自己的逻辑）。一部分引擎打整局，其余只打单场练习战，最难的战斗多练。
- 评估用训练权重的指数滑动平均（EMA），每步只算一次网络，取概率最高的动作，不搜索、不读档。直播用真实游戏，部分 Boss、精英战先短暂搜索；仓库里的记录都不搜索。
- 10 月 25 日起训练（故障机器人），租的 4090 和 3090；检查点编号是策略更新次数，到过 103,049。

没说的：72% 是哪个角色、多少局；奖励；PPO 参数；并行数和总局数；引擎速度。

- 玩家：**“现在结束回合会掉多少血”**、回合结束的自伤和格挡等。
- 手牌：当前显示的伤害和格挡（计入力量、易伤等修正后）、是否能打出。
- 抽牌堆：内容按 ID 排序，不给顺序。
- 地图：每个可去节点的**路线摘要**（离 Boss 几行、离最近火堆和商店几行、到下一个火堆前最少要打几个精英、最少几场战斗），加上整张地图。
- 商店、事件选项、卡牌选择的用途（升级、删除、变化……）。

我们的战斗观察（`combat_obs.cpp`）已经有意图的伤害、段数、类型，手牌的伤害和格挡，各牌堆内容，玩家和怪物的能力；**缺少**：招式 ID 和后续招式预测、“这回合还能打多少 / 能不能打死”、路线摘要。这些都只用公开信息和规则就能算，不违反 NoSL。

**防卡死规则**：评估里，敌人血量合计连续 20 个玩家回合没有创新低就判负；一个回合反复回到同一个局面就强制结束回合。他们有一局（Particle Wall+ 打出后回到手里）重复了几千次。我们也要有。

**我们的模拟器已经支持 A10**：`RunContext.init(seed, ascension)` 接受 0–10，地图（精英数、火堆数、第三幕第二个 Boss）、卡牌稀有度、药水栏等都按升阶处理；只是 Python 训练命令里没有 `--ascension`。A1–A10 规则有没有和原生逐项核对过，没有记录。

## 3. 本机吞吐实测（`train/scripts/bench_throughput.py`）

单线程，随机打法（局外和战斗都随机选合法动作，40 局，平均第 5.7 层就死，2,581 个决策）：

| 每个决策 | 微秒 |
| --- | ---: |
| 模拟器走一步（战斗 / 局外） | 4 / 4 |
| C++ 导出观察（战斗实体 / 局外） | 5 / 5 |
| Python 编码（`unified_obs`） | 24 |
| 整个循环（含以上与 Python 开销） | 154 |
| 拼批（`collate`，64 个一批） | 约 30–40 |

网络前向（本机 CPU 单线程，只说明相对大小；GPU 未测）：2.5M 约 2 毫秒/个，10.7M 约 6.6 毫秒/个，30.7M 约 14 毫秒/个。CPU 上推理不可行，必须集中到 GPU 成批算。

读法：随机打法的局面比真实局面小（牌少、早死），真实局面估计慢 2–3 倍，即单核每秒约 2,000–4,000 个决策。8 个核约 2–3 万/秒，够用。GPU 上 10–20M 网络推理每秒十万个级别是常见量级，但**未实测**；训练（前向加反向、每个样本 2 遍）会是另一个上限。

**训练机**：RTX 5090，WSL 里 8 个线程，这就是能用的全部配置（用户 2026-11-18 确认）。

## 4. 方案

### 4.1 网络

- 一个网络，输入沿用 `unified_obs`：战斗里是战斗实体（遭遇、玩家能力、手牌、抽牌堆、弃牌堆、消耗堆、待选牌、正在打出的牌、怪物、怪物能力、药水、遗物）加局外上下文（牌组、遗物、地图、幕、层）；局外是宏观观察。无历史。
- 加宽加深到 256–384 宽、各 4–6 层（10–30M）。先 256 × (4+4) 约 10.7M 起步，吞吐有余量再加。
- 输出：每个合法动作的分数（策略）、本幕 Boss 价值（已有，可留作辅助）、整局价值（新）。
- 局外和战斗共用编码器，策略头可以分开。

### 4.2 价值函数看隐藏信息（不违反 NoSL）

- 单独一个价值网络（或在同一网络上加只给价值头看的额外输入），额外看到：抽牌堆真实顺序、怪物下一招的真实结果、各随机数流的状态（只取能导出的部分）、还没揭开的事件与奖励等。
- 策略的输入不变，仍只有公开信息；出牌时不调用价值函数。所以实际下出的每一步仍然只用人能看到的信息。
- C++ 只新增导出接口，不改规则。

### 4.3 训练

- PPO，每次更新约 6.5 万个样本、2 遍（Zero-Search 的设置），GAE，γ 接近 1（2026-11-24 起改为两层时间尺度、折扣按层数，见 6.2 与 DEVLOG 52）。
- 奖励按 Zero-Search 的样子做成密集的：每层、精英、Boss、通关、死亡惩罚，加血量势函数（用户已同意密集奖励；具体权重实现时给用户确认）。
- 练习战：整局里每场战斗开始前存一个快照进池子；一部分引擎从池子里抽快照只打这一场，打完用价值函数估计战后状态来结算（和整局目标一致）。抽样时按最近的死亡率和掉血加权，Boss 和精英多练。快照约 0.6 MB 一个，池子要限制大小（或改存种子加决策序列）。
- EMA 权重用于评估和保存；评估取概率最高的动作，同时保留按概率采样的评估以便和以前比较。
- 起点：**从零**（用户已定；MCTS 教师数据已随翻新删除）。

### 4.4 工程（主要工作量）

- 多个工作进程，每个进程管几十到上百局，C++ 走模拟器、Python 编码；观察送到 GPU 统一推理，按批返回动作。
- 采样和训练交替（同步 PPO），或者采样一直跑、训练用稍旧的数据（异步，速度更快，需要修正）。先做同步的。
- 按工作日分段、到点保存、可接续，沿用现在的约定。

另一个风险：训练量大了以后，网络会找到模拟器的漏洞去钻（规则写错的地方），而且我们的模拟器还没有和原生游戏整局对照过，A1–A10 规则也没逐项核对。所以在模拟器里的胜率不一定等于真实游戏的胜率。异常和怪现象要盯着（例如某张牌的使用率异常高）。

## 6.2 训练框架设定（用户 2026-11-19）

**动手时机**：所有内容核对完之后再写训练框架，现在不写。

**必须保持可变**：奖励项可以随时加（每项一个独立函数和权重）；观察空间可以变（按观察版本区分，旧检查点明确拒绝）；价值函数看不看隐藏信息是开关。

**初始奖励**（Zero-Search 的数值，全部是参数）：每层 +0.01、精英 +0.02、Boss +0.1、通关 +1（2026-11-24 用户改为 **+1.6**，配合每层 0.99 的折扣，DEVLOG 53）、死亡 −0.1；血量势函数 0.1 ×（血量 / 最大血量）的变化，终局势能记 0。

**练习战**（用户 2026-11-19 晚改）：占环境 **40%**；输了 −0.1；赢了用战后状态的价值估计结算；抽样类型权重 **Boss 6、精英 3、普通 1**，再按最近死亡率和掉血加权。按一局约 15 普通、5 精英、4 Boss 估算，练习战里 Boss 约占 44%、精英和普通各约 28%。每次重放前重新打乱隐藏随机（抽牌顺序、战斗随机流），避免同一快照每次完全相同；现有 `BattleContext.resample_hidden` 是旧 MCTS 用的，用前要核对。观察里不加“这是练习战”的标记。

**防卡死**：敌人血量合计 20 个玩家回合未创新低判负；一回合内回到同一局面强制结束回合；一局最多 5,000 个决策；判负按死亡（−0.1）。

**价值头**：标量（预计还能拿到的奖励）；原三个 Boss 概率留作辅助输出。

**网络**：用户指定并于 2026-11-19 晚**拍板**（已知 3 天 A100 约 1 亿个决策、中档网络数据量多几倍，用户仍选 217M）：宽 768、局外 12 层 + 战斗 12 层，本机实测 **217.4M 参数**（其中 5.5M 是 ID 嵌入）。其他设置按比例：学习率 3e-5 加预热、梯度裁剪 1.0、每次更新 65,536 个样本 × 2 遍、小批 4,096（BF16 + 梯度累积）、截断 0.2 并加 KL 早停、γ 0.999、λ 0.95（2026-11-24 起默认改为两层时间尺度：每层 γ 0.99、战斗内 λ 0.95、局外 λ 按层 0.9，见 DEVLOG 52；旧做法 `--credit flat`）、熵 0.01 逐步降低、EMA 按约 2 小时的平均换算衰减率。检查点只留最新和 EMA 两份（含优化器约 3.5 GB）。

**速度风险（Claude 估算，未实测）**：按局外约 150、战斗约 50 个实体估，217M 每个决策前向约 36 GFLOP，加上训练约 250 GFLOP；5090 实际可能每秒几百个决策，是原计划“每秒 1 万”的几十分之一。瓶颈在 GPU，不在模拟器。对照：31.7M（384×6+6）、69.1M（512×8+8）。训练机测速后再定是否按 217M 开训。

## 6.5 两项硬要求（用户 2026-11-18 晚）

1. 模拟器可由人在命令行里操作：`train/spire_rl/play_cli.py`，已完成。
2. 训练出的 AI 能在带画面的原生客户端里玩：现在不做，但观察、动作、网络都不能走偏。约束见 `AGENTS.md` 第 3 节“可部署”；核实依据见 `DEVLOG.md` 第 17 节。

## 7. 放弃的

- **2026-11-19 再次确认放弃 MCTS 超级教师 / 战斗先验蒸馏**（用户提出“1B 搜索量、200 场 Boss 战记录教师决策，先训战斗先验”）。放弃理由：
  1. 我们的 MCTS 是每次模拟重采样隐藏信息的近似信息集搜索，叶子靠随机打到底；它不会收敛到最优，以前实测搜索量 ×4、×16 在 Boss 上没有显著提升。
  2. 本机实测单线程约 2,100–3,200 次模拟/秒，“每步 1B 次”做不完。
  3. 200 场约 1 万个决策，数据太少，网络只会记住那几套牌组。
  - 战斗先验的需求改由练习战（单场战斗 PPO，奖励密）满足。

- MCTS 打战斗、统一网络的 MCTS 教师 / 网络加搜索路线、small 网络、8 步历史、分叉：全部放弃，代码已在翻新时删除（git 分支 `v111_SF1` 可查）。
